| MVP de un Sistema Web para la Verificación de Integridad y Trazabilidad Documental en Contratos Laborales mediante Blockchain Permisionada | | | | | | |
| Cruce entre las disposiciones de la Ley 527 de 1999, el Decreto 2364 de 2012 y la Ley 1581 de 2012 con los requerimientos funcionales (RF) y no funcionales (RNF) del SRS v2. KPI-1.2: cobertura ≥ 90% de las disposiciones mapeadas. | | | | | | |

| LEY 527 DE 1999 - Mensajes de datos, comercio electrónico y firmas digitales | | | | | | |
| 1 | Ley 527/1999 | Art. 5° - Reconocimiento jurídico de los mensajes de datos | No se negarán efectos jurídicos, validez ni fuerza obligatoria a la información por el solo hecho de estar en forma de mensaje de datos. | Alcance general del sistema (RF-08 a RF-17) | El sistema trata el contrato en PDF como mensaje de datos con plena validez jurídica, sin exigir su materialización en papel para producir efectos probatorios. | Cubierto |
| 2 | Ley 527/1999 | Art. 6° - Escrito | El requisito de que la información conste por escrito se satisface si el mensaje de datos es accesible para su posterior consulta. | RF-18, RF-19, RF-37, RF-48 | Los módulos de consulta de documentos (empleado, verificador, administrador) garantizan acceso permanente a la información registrada, con nombre, identificador, fecha y estado. | Cubierto |
| 3 | Ley 527/1999 | Art. 7° - Firma | Cuando una norma exija firma, se entenderá cumplida si se usa un método que identifique al firmante y su aprobación del contenido (desarrollado por el Decreto 2364/2012). | Fuera del alcance funcional del MVP | El MVP no implementa firma electrónica avanzada; esta exclusión está declarada de forma explícita en el numeral 2.6.1 (Alcances) y 2.6.2 (Limitaciones) del anteproyecto. El sistema complementa, pero no reemplaza, los mecanismos de firma existentes. | Fuera de alcance |
| 4 | Ley 527/1999 | Art. 8° - Original | El mensaje de datos cumple el requisito de "original" si existe garantía confiable de que se conservó la integridad de la información desde su forma definitiva. | RF-14, RF-15, RF-16 | La huella criptográfica SHA-256 se genera al momento del registro y se ancla en la red Hyperledger Fabric, constituyendo la garantía confiable exigida por la norma. | Cubierto |
| 5 | Ley 527/1999 | Art. 9° - Integridad de un mensaje de datos | La información es íntegra si ha permanecido completa e inalterada, salvo cambios propios de la comunicación, el archivo o la presentación. | RF-14, RF-30, RF-31, RF-32, RF-34, RNF-05, RNF-14 | La comparación automática de hashes (registrado vs. recalculado) detecta cualquier alteración y actualiza el estado del documento a Verificado o Alterado. | Cubierto |
| 6 | Ley 527/1999 | Art. 10 - Admisibilidad y fuerza probatoria de los mensajes de datos | Los mensajes de datos son admisibles como medio de prueba y su fuerza probatoria se rige por las reglas procesales generales. | RF-21, RF-22, RF-35, RNF-26, RNF-27 | El historial de trazabilidad (acción, usuario, txID, fecha) recuperado desde el ledger constituye el soporte probatorio del documento y de sus eventos. | Cubierto |
| 7 | Ley 527/1999 | Art. 11 - Criterio para valorar probatoriamente un mensaje de datos | Para valorar la fuerza probatoria se considera la confiabilidad en la generación, archivo y comunicación del mensaje, la integridad conservada y la identificación del iniciador. | RF-13, RF-22, RF-35, RNF-06 | El registro de metadatos (usuario responsable, fecha) y el txID de cada transacción permiten identificar de forma confiable al iniciador de cada acción. | Cubierto |
| 8 | Ley 527/1999 | Art. 12 - Conservación de los mensajes de datos y documentos | El deber de conservación se satisface si la información permanece accesible para su posterior consulta durante el tiempo requerido. | RF-18, RF-37, RF-48, RNF-12 | Los módulos de consulta documental mantienen disponible el historial de documentos y su estado durante todo el período de validación del MVP. | Cubierto |
| DECRETO 2364 DE 2012 - Firma electrónica (reglamenta el Art. 7° de la Ley 527/1999) | | | | | | |
| 9 | Decreto 2364/2012 | Art. 2° - Neutralidad tecnológica | Ninguna disposición del decreto puede excluir o restringir un método tecnológico que cumpla los requisitos de firma electrónica del Art. 7° de la Ley 527/1999. | Fuera del alcance funcional del MVP | Al no implementarse firma electrónica, este principio no aplica de forma directa al sistema; se deja constancia de que su futura incorporación no está restringida por el diseño actual (arquitectura modular, RNF-19, RNF-22). | Fuera de alcance |
| 10 | Decreto 2364/2012 | Art. 3° - Cumplimiento del requisito de firma | El requisito de firma se cumple con una firma electrónica que sea tan confiable como apropiada para los fines del mensaje de datos. | Fuera del alcance funcional del MVP | Documentado como limitación explícita (numeral 2.6.2): el sistema no sustituye los mecanismos de firma electrónica, solo genera evidencia de integridad posterior al registro. | Fuera de alcance |
| 11 | Decreto 2364/2012 | Art. 5° - Efectos jurídicos de la firma electrónica | La firma electrónica que cumpla los requisitos del Art. 3° tendrá la misma validez y efectos jurídicos que la firma manuscrita. | Fuera del alcance funcional del MVP | No aplica de forma directa; el sistema no emite ni valida firmas electrónicas. | Fuera de alcance |
| 12 | Decreto 2364/2012 | Art. 6° - Obligaciones del firmante | El firmante debe mantener control y custodia sobre sus datos de creación de firma y actuar con diligencia para evitar su uso no autorizado. | RF-02, RF-03, RF-04, RF-52, RF-53, RNF-01, RNF-02, RNF-07 | La autenticación con credenciales + segundo factor (token al correo corporativo) y la gestión segura de contraseñas trasladan el principio de custodia de credenciales del firmante al esquema de autenticación del sistema. | Cubierto parcialmente |
| LEY 1581 DE 2012 - Protección de datos personales | | | | | | |
| 13 | Ley 1581/2012 | Art. 3° - Definiciones (Tratamiento de datos personales) | Define "Tratamiento" como cualquier operación sobre datos personales (recolección, almacenamiento, uso, circulación, supresión, etc.). | RNF-04, RNF-08 | El sistema evita almacenar el contenido de los contratos (que incluye datos personales del trabajador) tanto en MongoDB en texto plano expuesto como en la blockchain; solo registra la huella criptográfica y metadatos mínimos. | Cubierto |
| 14 | Ley 1581/2012 | Art. 4° lit. b) - Principio de finalidad | El tratamiento debe obedecer a una finalidad legítima e informada al titular. | RF-13 | El registro de metadatos se limita a lo estrictamente necesario para identificar y verificar el documento (identificador, nombre, usuario responsable, fecha). | Cubierto |
| 15 | Ley 1581/2012 | Art. 4° lit. g) - Principio de seguridad | La información personal debe manejarse con medidas técnicas, humanas y administrativas que eviten su adulteración, pérdida, consulta o uso no autorizado. | RNF-01, RNF-03, RNF-05, RNF-07 | Hashing seguro de contraseñas, control de acceso basado en roles (RBAC), gestión segura de sesiones e inmutabilidad de la evidencia en blockchain. | Cubierto |
| 16 | Ley 1581/2012 | Art. 4° lit. h) - Principio de confidencialidad | Quienes intervengan en el tratamiento deben garantizar la reserva de la información, incluso después de finalizada su relación con el proceso. | RF-27, RNF-08 | La huella criptográfica completa y los datos del documento solo son visibles para roles autorizados (Verificador, Administrador), de acuerdo con reglas de acceso definidas. | Cubierto |
| 17 | Ley 1581/2012 | Art. 17 - Deberes de los Responsables del Tratamiento | Deberes de garantizar el ejercicio de los derechos del titular, usar los datos solo para los fines autorizados y mantener condiciones de seguridad. | RF-45, RF-46, RF-47, RNF-03 | La gestión administrativa de usuarios (creación, edición, desactivación lógica sin eliminar la trazabilidad histórica) da soporte operativo a estos deberes dentro del alcance del MVP. | Cubierto |

| NOTA DE ALCANCE NORMATIVO, ISO/IEC 27001:2022 | | | | | | |
| Esta matriz no incluye los controles A.8.24 y A.8.11 del Anexo A de ISO/IEC 27001:2022. De acuerdo con el numeral 2.6.2 (Limitaciones) del anteproyecto, dichos controles se referencian únicamente como criterios de diseño (ver RNF-30) y el proyecto no implementa ni evalúa el Sistema de Gestión de Seguridad de la Información (SGSI) completo, no realiza auditorías de cumplimiento normativo ni obtiene certificación asociada a la norma. Incluir filas de "cobertura" para estos controles equivaldría a afirmar una auditoría de cumplimiento que el proyecto declara explícitamente fuera de alcance. El KPI-1.2 de cobertura normativa (≥90%) se calcula exclusivamente sobre Ley 527/1999, Decreto 2364/2012 y Ley 1581/2012, consistente con la definición del indicador. | | | | | | |
